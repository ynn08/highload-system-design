Выбор баз данных (Хранилища)
PostgreSQL (Primary DB для сервисов Orders, Payments, Users)

Паттерн доступа: Преимущественно запись и точечное чтение. Необходимы строгая консистентность, поддержка транзакций и ACID (для оплат и статусов заказа).
Обоснование: Реляционная БД — индустриальный стандарт для хранения финансовых и транзакционных данных. Гарантирует сохранность заказов (Durability 99.999999% из НФТ-004).
Elasticsearch (Search Engine для Catalog Service)

Паттерн доступа: Read-heavy (90% всех запросов платформы). Поиск с фильтрацией и гео-запросы.
Обоснование: Позволяет легко комбинировать полнотекстовый поиск по названию с гео-фильтрацией (поиск в радиусе N км) и фильтрацией по массивам (кухни). Обеспечивает SLO (p99 < 200ms) на сложных запросах, чего трудно добиться в PostgreSQL при 5000 RPS.
Redis (In-Memory Cache для корзин и сессий)

Паттерн доступа: Частые мелкие перезаписи (добавление/удаление блюд в корзину).
Обоснование: Данные корзины эфемерны, к ним нужен доступ с минимальной задержкой (p99 < 200ms для ФТ-003). Хранение в оперативной памяти с TTL (Time To Live) — идеальный паттерн.

Модель данных
Ниже представлены 4 основные сущности, распределенные по выбранным базам данных.

1 Сущность: orders (БД: PostgreSQL)
Хранит основную метаинформацию о заказе.

Объём данных: ~400 000 записей/день (~146 GB/год без репликации, данные из Capacity Estimation).
Поля:
order_id (UUID, Primary Key)
customer_id (UUID, Foreign Key -> users.id)
restaurant_id (UUID, Foreign Key -> restaurants.id)
status (VARCHAR) — текущий статус (PENDING, PAID, DELIVERING, COMPLETED)
total_amount (DECIMAL) — сумма заказа
created_at (TIMESTAMP)
Индексы:
idx_customer_id (B-Tree по customer_id) — Обоснование: необходимо для быстрой загрузки истории заказов конкретного пользователя.
idx_status_created_at (Составной индекс по status + created_at) — Обоснование: нужен для фоновых джобов (например, поиск зависших в PENDING заказов старше 15 минут для отмены).
2 Сущность: order_items (БД: PostgreSQL)
Хранит состав каждого заказа (связь один-ко-многим с orders).

Объём данных: ~1.2 млн записей/день (в среднем 3 блюда на заказ), ~200 GB/год.
Поля:
item_id (UUID, Primary Key)
order_id (UUID, Foreign Key -> orders.order_id)
menu_item_id (UUID) — ссылка на блюдо из каталога
quantity (INT)
price_at_checkout (DECIMAL) — фиксация цены на момент заказа
Индексы:
idx_order_id (B-Tree по order_id) — Обоснование: используется при каждом чтении заказа для быстрого получения списка его позиций (JOIN или прямой Select).
3 Сущность: restaurants_index (Документ в Elasticsearch)
Денормализованный документ, используемый Catalog Service для поиска.

Объём данных: ~20 000 - 50 000 ресторанов. Объём небольшой (< 1 GB), но огромная нагрузка на чтение (до 5000 RPS).
Поля (Mapping):
restaurant_id (Keyword, Document ID / PK)
name (Text) — название ресторана
location (Geo-point) — координаты (lat, lon)
cuisines (Keyword Array) — список кухонь ["Burger", "American"]
rating (Float)
Индексы (встроенные в Elastic):
Inverted Index по name — Обоснование: для полнотекстового поиска с учетом опечаток.
Geo-spatial Index (Bkd-tree) по location — Обоснование: для быстрого отсечения ресторанов, находящихся вне зоны доставки пользователя.
4 Сущность: carts (Хранилище: Redis)
Корзина пользователя. Хранится в формате Key-Value (Hash).

Объём данных: ~2 000 000 DAU = ~2 млн активных ключей. Размер в памяти ≈ 2-4 GB.
Поля:
Ключ (Key): cart:{customer_id} (по сути, выполняет роль PK / Partition Key)
Значение (Value): JSON строка или Redis Hash:
json
{
  "restaurant_id": "uuid",
  "items": { "menu_item_id": 2, "menu_item_id_2": 1 }
}
TTL (Time to Live): 7 дней.
Индексы: Не требуются, так как доступ всегда происходит по точному ключу (O(1)). Обоснование: Redis выступает как In-Memory хранилище прямого доступа.
