Название: Паттерн обработки заказов и оплат

Контекст (Context):
Согласно расчету бюджета задержки (Capacity Estimation из Задания 1), синхронное оформление заказа не укладывается в SLO (p99 < 800ms) из-за узкого места — ожидания ответа от внешнего Payment Provider API (~300ms + сеть). Нам нужно надежно сохранять заказы (Durability 99.999999%) и не заставлять клиента ждать ответа от банка в синхронном запросе на создание заказа.

Альтернативы (Alternatives):

Синхронный вызов с 2-Phase Commit (2PC): Минусы: Блокировки таблиц, крайне низкая производительность, невозможно использовать в распределенных системах и с внешним платежным шлюзом.
Асинхронная хореография (Choreography): Каждый сервис сам слушает события. Минусы: Сложно отследить общий статус заказа, нет единого места, где описан бизнес-процесс.
Асинхронная оркестрация (Saga Orchestration): Использование паттерна Saga. Order Service выступает оркестратором: создает заказ в статусе PENDING, отправляет событие в брокер, возвращает пользователю 201 Created (быстро), а Payment Service общается с Платёжным шлюзом в фоне.
Решение (Decision):
Выбран подход Асинхронная оркестрация (Saga Orchestration) через брокер сообщений (Apache Kafka или RabbitMQ).

Последствия (Consequences):

Плюсы: Решает проблему SLO — пользователь мгновенно получает ответ 201 Created, задержка API Gateway < 200ms. Повышается надежность при интеграции с внешним Платёжным шлюзом (можно использовать retry без таймаута для клиента).
Минусы: Необходимо реализовать компенсирующие транзакции (компенсации). Если оплата отклонена внешним шлюзом, оркестратор должен отправить команду на отмену заказа и очистку резерва.
