Название: Выбор базы данных для каталога ресторанов

Контекст (Context):
ФТ-001 требует поиска ресторанов по названию, кухне, рейтингу и расстоянию (гео-поиск). Задержка должна быть p99 < 200ms. Нагрузка на чтение составляет 90%, пиковый RPS достигает 4166. Требуется сложный многокритериальный поиск.

Альтернативы (Alternatives):

Реляционная БД (PostgreSQL) с расширением PostGIS: Плюсы: Надежность, ACID. Минусы: Полнотекстовый поиск реализован базово, при 5000 RPS на сложные гео-запросы с текстовым поиском потребуются массивные шардированные кластеры, что дорого и сложно.
Документная БД (MongoDB): Плюсы: Встроенные гео-индексы 2dsphere. Минусы: Полнотекстовый поиск уступает специализированным движкам, сложнее ранжировать результаты по релевантности и рейтингу одновременно.
Поисковый движок (Elasticsearch / OpenSearch): Плюсы: Специализирован под полнотекстовый поиск, фасетную фильтрацию и гео-запросы. Легко масштабируется горизонтально под read-heavy нагрузку.
Решение (Decision):
Выбран Elasticsearch в качестве основного хранилища для чтения (Read Model) каталога ресторанов.

Последствия (Consequences):

Плюсы: Гарантированное выполнение SLO (p99 < 200ms) на сложных выборках (текст + радиус доставки + рейтинг). Гибкая настройка релевантности выдачи.
Минусы: Elasticsearch не является надежным первичным хранилищем (Source of Truth). Потребуется держать первичные данные о ресторанах в реляционной БД (например, PostgreSQL) и реализовывать механизм синхронизации (например, CDC - Change Data Capture через Debezium) в Elasticsearch.
